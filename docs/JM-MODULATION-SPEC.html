Modulation:
LFO, Matrix & Arp

Three features exist as buttons in the approved interface but have never been specified: MOD MATRIX, LFO and ARP. This document proposes what they should be, so the design is agreed before any of it is built.

Status  Awaiting approval Scope  JM Signature only Authority  Extends JM-BUILD-SPEC.md

AThe short version

The modulation matrix is not a new system. The macro system already built is a modulation matrix with exactly one kind of source — a knob you turn by hand. Every row already carries a destination path, a bipolar depth, a range, a curve and an invert flag, and all of it already serializes into presets and plugin state.

The whole proposal in one line

Generalise the existing macro target into a source → destination row, then add LFOs and note-derived sources as new source types. The arpeggiator is separate work and should be treated as such.

That framing matters commercially as well as technically: it means the matrix inherits drag-and-drop assignment, the target editor, host automation and preset compatibility for free, rather than growing a second parallel system that has to be kept in step with the first.

BSources — what can modulate

Twelve sources. The four gold-edged ones already exist and are simply reclassified; the rest are new. Every source produces a normalised value that feeds the existing target model unchanged.

Mod wheel and expression are listed because promoting them into the matrix lets a player re-route them freely, while their existing per-world defaults stay as shipped. Nothing that works today stops working.

One honest constraint

These are global LFOs: one phase, shared by every sounding voice. That is the right default and it is cheap. It also means Every note retrigger restarts the shared phase rather than giving each note its own — so true per-voice vibrato, where a note struck late has its own independent cycle, is not covered.

Per-voice LFOs are a materially larger job: an oscillator per voice across a 64-voice, 4-slot engine, plus the modulation having to be applied per voice rather than once per block. For a sampled instrument the global version covers most real use. This is decision 1 below.

DModulation matrix

Eight rows. Each row is the existing target structure with a source attached — meaning the data model gains one field and the rest is already written and already tested.

Behaviour

  • Summing. Several rows may target one parameter; contributions add, then clamp to the parameter's own range. This is what allows an LFO to wobble a value a macro is simultaneously sweeping.
  • Modulation never overwrites the knob. The knob keeps the value the player set; modulation offsets from it. Turning the knob while modulation runs moves the whole modulated range, which is what a player expects.
  • Cross-modulation. LFO rate and depth are themselves valid destinations, so a slow LFO can sweep a fast one. Guard against a row modulating its own source.
  • Assignment. Three routes, mirroring what macros already do: drag a source chip onto any knob, pick from the row's dropdowns, or right-click a parameter and choose a source.
  • Display. A modulated knob shows its base value as the pointer and the modulation span as a second arc, so the player can see the range being swept. This is the one genuinely new piece of UI drawing.

EArpeggiator

Deliberately a classic arpeggiator, not a step sequencer. One arp, global, with a per-slot enable so it can drive slot C while A and B stay held — the common performance case.

Two interactions worth naming now

  • Sustain pedal. With the arp running, CC64 should latch notes into the arpeggio rather than sustaining each step's tail — the standard behaviour, and different from the sustain logic already specified for normal play. It needs to be written down before it is built.
  • Transport. In a DAW the arp locks to the host play position, so a pattern starts on the beat when the transport rolls. In standalone it free-runs from the first note.

FWhere the settings live

All three panels open from the bottom-bar buttons that already exist and are currently disabled, using the same overlay treatment as the macro editor and settings window. No new navigation, no change to the approved arrangement.

Plugin state and performance presets carry the whole modulation setup. State is versioned so presets saved today still load — a plain requirement, but one that is much cheaper to honour now than to retrofit.

A format decision that reaches JM Capture

Instrument bundles carry presets too, and their schema is shared with JM Capture. Adding modulation to it would oblige Capture to understand LFOs and arpeggios it does not have. Recommendation: keep modulation out of .jmi bundle presets entirely. It belongs to the performance layer — the player's setup — not to the instrument's sample set. This is decision 4.

GBuild order

Two phases, because the first two features are one system and the third is not.

Phase 1

LFOs and the matrix, together

They ship as one piece of work: an LFO with nothing to modulate is untestable, and a matrix whose only sources are the existing macros adds little. Bulk of the effort is the source abstraction and the modulated-value knob display; the row model, assignment and serialization already exist.

Phase 2

Arpeggiator

Independent of the matrix and can follow it without rework. Its real risk is timing — host sync, swing and the pedal-latch behaviour — which wants unhurried testing against a DAW rather than being rushed alongside the modulation work.

HDecisions needed

Five open questions. Each has a recommendation; none needs a long answer.

1

Global LFOs, or per-voice? open

Global is cheap and covers most use. Per-voice gives true independent vibrato per note, at a substantially higher cost across a 64-voice, four-slot engine.

Recommend global for now, revisited only if it sounds limiting in playing.

2

One arpeggiator, or one per slot? open

Four independent arps allow polyrhythms across stacked sounds. One arp with per-slot enable covers the common case at a fraction of the complexity.

Recommend one global arp with per-slot enable.

3

Eight matrix rows, or sixteen? open

Eight fits the screen without scrolling and covers ordinary patches. Sixteen suits sound designers and needs a scrolling list.

Recommend eight, with the row count stored so it can grow later without breaking presets.

4

Should bundle presets carry modulation? open

Doing so would change the format shared with JM Capture and require Capture to model features it does not have.

Recommend no — modulation stays in the plugin's own presets.

5

Is the mod envelope in or out? open

A second envelope is genuinely useful for per-note sweeps, but it is the one source with a per-voice cost, and velocity already covers much of the same ground on a sampled instrument.

Recommend cutting it from the first release and adding it if the matrix proves it is missed.

IWhat this does not include

  • A step sequencer. The arp is an arpeggiator. Per-step pitch, gate and velocity editing is a different feature with a different interface.
  • Modulation of the sample engine's internals. Destinations are the parameters already exposed on the model pages and FX rack, not zone selection or round-robin behaviour.
  • Anything in JM Capture. Capture shapes what it records; it has no performance layer and gains nothing from an arpeggiator.
  • MPE. Per-note expression is a larger architectural question and is not assumed here.
